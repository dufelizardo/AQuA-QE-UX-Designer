# Agent Design

> Estrutura conforme `../standards/agent_design_standard.md`. Decisões de design centrais do agente.

1. **Um único artefato nesta fase** — igual ao Solution Architect, o UX Designer gera só a UX Specification nesta fase. Simplifica o CLI (sem `--modo`) e o orquestrador (uma única sequência de skills).
2. **Personas e User Journeys são consumidos, nunca gerados** — decisão de design mais importante do agente. O PRD do Product Manager já produz ambos (`synthesize_personas`, `identify_user_journeys`); regerá-los aqui criaria duas fontes divergentes do mesmo artefato. `extract_ux_context` extrai as seções já existentes do texto do PRD como contexto de leitura, nunca chama uma skill equivalente a `synthesize_personas`.
3. **User Flow é mais granular que User Journey, não um sinônimo** — a Journey do PM é de nível de negócio/emocional (ex.: "o cidadão journey de perceber o problema até o pós-atendimento"); o Flow do UX Designer é de nível de navegação concreta para uma Story específica (ex.: as telas exatas de "agendamento assistido presencial"). Essa diferença de granularidade é o que justifica a existência do agente sem duplicar o PM.
4. **"Teste de Usabilidade" reformulado como revisão heurística de especialista** — o agente não tem acesso a usuários reais, então não pode conduzir nem relatar um teste de usabilidade genuíno. `review_ux_specification` aplica as 10 Heurísticas de Nielsen como avaliação de especialista simulada — sempre rotulada como tal, nunca apresentada como se usuários reais tivessem sido observados (ver GR-UX-3).
5. **Acessibilidade é recomendação, nunca certificação** — `review_accessibility` fundamenta suas recomendações em WCAG 2.1, mas nunca afirma "este fluxo está em conformidade com WCAG AA" como fato — sempre como algo a verificar por um humano/ferramenta de auditoria real (ver GR-UX-2).
6. **Wireframes/Protótipos/Design System ficam fora, não por serem menos importantes, mas por exigirem uma integração que a plataforma ainda não tem** (Figma). Diferente das decisões de escopo "permanentemente fora" (Personas/Journeys, pesquisa/teste real), esta é uma decisão de **fase**: nasce como agente irmão futuro (AQuA-QE UI Designer) quando essa integração for construída — mesmo princípio de "entregar o que cabe no padrão estabelecido primeiro" já usado pelo Solution Architect com Jira (só leitura) e pelo Product Owner com a camada Feature.
7. **Aprovar automaticamente vs. exigir revisão humana** — o agente **nunca** decide aprovação final. `validate_ux_specification` decide apenas se a UX Specification passa no checklist automático (nível "rascunho validado"); a aprovação de negócio/design permanece sempre humana.
8. **Revisão e refinamento atuam sobre a UX Specification inteira, nunca etapa por etapa** — mesma razão de design do Solution Architect: não há aqui uma unidade intermediária cara o suficiente (como o Épico no PO) para justificar um checkpoint de recepção por etapa. `review_ux_specification` avalia o conjunto (fluxos + arquitetura da informação + acessibilidade) em uma única chamada; `refine_ux_specification` reescreve os campos afetados em uma única chamada.
